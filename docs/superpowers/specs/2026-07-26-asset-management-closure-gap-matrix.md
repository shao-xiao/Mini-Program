# DHIC 资产管理闭环差异矩阵

日期：2026-07-26

## 1. 产品边界

资产管理定位为“资产基础数据中心 + 财务计费依据来源 + 小程序业务数据来源”。

- 资产模块维护楼宇、楼层、房间、设备、表具、停车位、会议室及其有效期关系。
- 资产模块确认可计费业务事实并保存面积、用量、价格、时长和业务主体快照。
- 财务模块是唯一将 `asset_charge_basis` 转为统一 `bill` 的模块。
- 小程序只按 `/mobile/me` 的身份、capabilities 和服务端派生数据范围读取业务数据。

## 2. 审计差异矩阵

| 模块 | 改造前现状 | 主要缺口或风险 | 闭环实现 |
|---|---|---|---|
| 楼宇空间 | 楼宇、楼层、房间已有层级；房间主要使用通用 `area` | 物业费计费面积来源不明确；房间编号唯一范围不准确；历史面积缺少统一依据快照入口 | `building_room.property_fee_area` 为唯一物业费面积来源；同楼层房号唯一；计费计划和资产依据保存面积/单价/房号快照 |
| 设备台账 | 有设备基本资料和位置文本 | 仅靠文本无法稳定关联楼宇、楼层、房间；图片附件与责任信息不完整 | 增加标准楼宇/楼层/房间关系、位置类型、序列号、责任部门/人员、使用年限、图片和附件 |
| 能耗 | 有表具和月度抄表，表具可直接覆盖当前租户；抄表曾直接进入能耗账单逻辑 | 租户变化会丢历史主体；读数修改缺审计；能源价格变化可能影响历史解释；资产页与财务边界重叠 | 新增 `energy_meter_binding` 有效期历史、`energy_reading_audit`、来源/附件/归零原因；确认抄表只形成 `ENERGY` 计费依据，财务统一生成账单 |
| 停车 | 有车位、分配、停车账单；有效关系以停车位当前状态为主 | 当前租户覆盖式关系；联系人、移动用户、车辆和价格快照不完整 | `parking_assignment` 保存租户、联系人、移动用户、车辆、有效期、规则和单价快照；有效绑定唯一；同步只形成 `PARKING` 依据 |
| 会议 | 有会议室和预约，价格主要在会议室当前字段 | 缺收费规则历史；预约价格和时长快照不足；并发冲突仅靠前置查询风险较高 | 新增 `meeting_rate_rule`；预约保存规则、单价、时长、金额和联系人快照；事务内锁定会议室并复检冲突；确认预约形成 `MEETING` 依据 |
| 财务 | `bill`、支付、开票和核销体系已存在 | 多个资产页面可能各自复制生成/收款逻辑 | 新增统一 `asset_charge_basis`；财务工作台负责读取依据、生成 `bill` 并回写 BILLED，资产页面不维护收款/发票/核销 |
| 小程序 | 已有微信会话、手机号登录、TENANT/PUBLIC 和部分 INTERNAL 兼容；会议/账单已有页面 | STAFF 对外命名、租户负责人/员工范围、能耗和停车真实接口不完整 | 对外统一 PUBLIC/TENANT/STAFF；`/mobile/me` 返回联系人角色、员工信息、capabilities、dataScope；新增能耗和停车页面及服务端派生范围接口 |
| 字段平台 | 已有 ModuleFieldRegistry、WorkspaceConfig、自定义字段和统一附件能力 | 资产模块字段定义覆盖不全 | 房间、设备、能耗、停车、会议注册到现有 Module Schema；管理端 WorkspaceConfig 与小程序字段继续使用同一 fieldKey |

## 3. 历史兼容原则

- V45 只新增表、字段、索引和兼容回填，不修改已执行迁移。
- 已有房间面积回填到 `property_fee_area`，后续计费使用快照。
- 已有表具当前租户关系转为首条有效期绑定，旧字段暂留作兼容读取。
- 已有停车月费回填为绑定单价快照。
- 已有会议室小时价转为首条收费规则，预约回填单价、时长和金额快照。
- 不删除、不清空、不重写历史财务账单。

## 4. 尚需环境验收

- 11 个显式 MySQL 集成测试默认跳过；V45 尚未对本地 MySQL 8 开发库实际执行。
- STAFF 目前按 RBAC capability 控制移动能力，但现有数据模型没有可复用的组织字段，能耗的更细组织范围仍需后续模型确认。
- 浏览器和微信开发者工具验收需要本地服务、开发库、微信 AppID/会话及四类测试身份。
